# Authentication (аутентификация)
## Что это - способы, которыми сервер убеждается, кто ты, при каждом запросе 

### Basic Authentication - самый простой, встроен в сам HTTP:
```bash
Authorization: Basic YWRtaW46MTIzNDU=
```
Строка после Basic - это username:password? закодированные в Base64.Basic Auth безопасен только поверх HTTPS - по обычному HTTP пароль фактически передается в открытом виде
Base64 - это не шифрование, это просто кодирование, декодируется мгновенно любым онлайн-декодером

### Session-based Authentication - то, что мы уже разобрали подробно (Cookies/Sessions): логинишься один раз, сервер выдает куку с session ID, дальше куку подтверждает личность на каждый запрос. Сервер хранит состаяние у себя.

### Token-based Authentication (JWT - JSON Web Token) - принципиально другой подход:
```bash
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...
```
Токен состоит из трех частей, разделеных точками: header.payload.signature. В отличие от сессии, серевер ничего не хранит у себя - все информация о пользователе закодирована прямо внутри токена, а подпись гарантирует, что токен не был подделан.

### API Key - простой статичный ключ, обычно для доступа программ (не людей) к API:
```bash
X-API-Key: sk_live_abc123xyz
```

### Multi-Factor Authentication(MFA/2FA) - дополнительный фактор поверх пароля - не про протокол HTTP как таковой,  а про процесс проверки личности перед выдачей сессии/токена

# Same-Origin Policy (SOP)
## Что это - Ключевой браузерный механизм безопасности: скрипт с одного origin не может по умолчанию обращаться к ресурсам другого origin

### Origin = протокол + домен + порт, все три компонента должны совпадать:
```bash
https://example.com:443  и  http://example.com:443   → РАЗНЫЙ origin (протокол)
https://example.com      и  https://api.example.com  → РАЗНЫЙ origin (поддомен ≠ основной домен)
https://example.com:443  и  https://example.com:8080  → РАЗНЫЙ origin (порт)
```
Зачем нужен:
  - без SOP любой сайт, который ты открыл, мог бы через JavaScript читать данные с других сайтов, где ты залогинен (почта, банк) - просто отправив fetch-запрос и прочитав ответ. SOP это блокирует на уровне браузера
Важный нюанс:
  - SOP не блокирует сам запрос, а блокирует чтение ответа JavaScript'ом с другого origin. Это тонкое ,но важное различие - картинки/скрипты/CSS с других доменов подгружаюся нормально (<img>,<script src>), а вот прочитать содержимое ответа через fetch()/XMLHttpRequest с другого origin — нельзя
CORS (Cross-Origin Resource Sharing):
  - управляемое исключение из SOP.Сервер явно разрешает конкретным origin'ам обращатся к себе:
    ```bash
    Access-Control-Allow-Origin: https://trusted-site.com
    ```

### Практическая уязвимость - неправильно настроенный CORS (например, Access-Control-Allow-Origin: *) на эедпоинте, который отдает приватные данные пользователя вместе с Access-Control-Allow-Credentials: true) - классическая дыра, позволяюая вредоносному сайту читать чужие данные через JS

# Браузер и сервер — итоговая картина всего этапа
## Теперь когда все кусочки разобраны, соберем все в единый процесс:
1. Мы вводим URL -> браузер резолвит домен через DNS (глава 2 моего OSINT-курса)
2. Устанавливается TCP-соединение + TLS-рукопожатие(если HTTPS)
3. Браузер отправляет HTTP Request: метод,заголовки,куки,параметры
4. Сервер обрабатывает запрос, при необходимости проверяет Authentication (кука/токен/Basic Auth)
5. Сервер возвращает HTTP Response: статус-код, заголовки, тело
6. Браузер рендерит ответ, если это HTML со встроенным JS - это JS подчиняется Same-Origin Poplicy при любых собственных запросах к другим доменам
7. Если сервер поставил куку - браузер сохраяняет ее согласно атрибутам и автоматически приклавдывает к следующим запросам на тот же origin
