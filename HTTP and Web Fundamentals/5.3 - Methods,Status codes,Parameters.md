# Methods(HTTP-методы)
Метод в стартовой строке запроса говорит серверу, что имменно нужно сделать с ресурсом

## Методы:
1. GET - получить данные. Не должен менять состояние сервера (idempotent и safe в терминологии HTTP). Параметры - в URL
   ```bash
   GET /users?id=42 HTTP/1.1
   Host: example.com
   ```
2. POST - отправить данные, создать что-то новое(регистрация, комментарий, логин).Данные — в теле запроса, не в URL
   ```bash
   POST /login HTTP/1.1
   Host: example.com
   Content-Type: application/x-www-form-urlencoded

   username=admin&password=12345
   ```
3. PUT - заменить ресурс целиком.Idempotent (повторный такой же запрос даёт тот же результат — ресурс просто ещё раз перезапишется тем же значением)
4. PATCH - обновить ресурс частично (например, поменять только email, не трогая остальные поля профиля)
5. DELETE - удалить ресурс
6. HEAD - как GET, но сервер возвращает только заголовки, без тела
7. OPTIONS - спросить сервер, какие методы вообще поддерживаются:
   ```bash
   OPTIONS /api/users HTTP/1.1
   ```
   ответ может содержать:
   ```bash
   Allow: GET, POST, OPTIONS
   ```
8. Идемпотентны: GET, PUT, DELETE, HEAD, OPTIONS
9. НЕ идемпотентен: POST, PATCH (обычно)

### Практический момент для безопасности:
Если OPTIONS-запрос показывает, что DELETE или PUT доступны на эндпоинте, который не должен их поддерживать(например, публичный API без авторизации) - это повод присматреться внимательнее, возможная уязвимость

# Status codes (коды статуса)
Первая цифра = категория ответа

## Codes
1xx - информационный(редко видно вручную)
  - 100 Continue - сервер получил начало запроса, продолжай отправку
  - 101 Switching Protocols - переключение, например на WebSocket
    
2xx - успех
  - 200 OK - все прошло успешно
  - 201 Created - новый ресурс создан
  - 204 No Content - успех, но тело ответа пустое
    
3xx - редирект
  - 301 Moved Permanently - ресурс переехал навсегда
  - 302 Found - временный редирект
  - 304 Not Modified - ресурс не менялся с последнего запроса, можно использовать кэш
    
4xx - ошибка клиента
  - 400 Bad Request - запрос некорректно сформирован
  - 401 Unauthorized - нужна аутентификация (ты не залогинен)
  - 403 Forbidden - сервер знает, кто ты, но доступ запрещён
  - 404 Not Found - ресурс не существует
  - 429 Too Many Requests - превышен лимит запросов
    
5xx - ошибка сервера
  - 500 Internal Server Error - сервер сломался
  - 502 Bad Gateway - прокси/шлюз получил невалидный ответ от вышестоящего сервера
  - 503 Service Unavailable - сервер временно недоступен
    
Частая путаница между 401 vs 403:
  - 401 - "я не знаю кто ты, сначала авторизуйся"
  - 403 - "я знаю кто ты, но тебе сюда нельзя"

# Parameters (параметры)  
1. Query-параметры — видны прямо в URL после ?: 
```bash
https://example.com/search?query=cat&page=2&sort=asc
```
Разделяются &, каждый в формате ключ=значение
2. Body-параметры — в теле запроса, обычно с POST/PUT/PATCH:
```bash
POST /register HTTP/1.1
Content-Type: application/json

{"username": "kosta", "email": "kosta@mail.com"}
```
3. Path-параметры — часть самого URL-пути:
```bash
/users/42/orders/7

42 и 7 — идентификаторы, встроенные прямо в структуру пути
```
4. Headers как параметры — иногда данные передаются и через заголовки:
```bash
Authorization: Bearer eyJhbGc...
X-API-Key: abc123
```

# Почему параметры критичны для безопасности:
Это данные, которые пользьзователь полностью контролирует. Если сервер доверяет им без проверки - открывается путь к SQL injection(?id=1 OR 1=1), path traversal (?file=../../etc/passwd),и другим классическим уязвимостям
