# Cookie 
## Что это - это маленький кусочек данных (обычно текстовая строка вида key=value), который сервер сохраняет в браузере через заголовок ответа Set-Cookie, а браузер потом автоматически прикладывает ее к каждой следующему на тот же сайт

Пример - сервер ставит куку:
```bash
HTTP/1.1 200 OK
Set-Cookie: session_id=abc123xyz; Path=/; HttpOnly; Secure; SameSite=Lax
```
Дальше браузер сам прикладывает ее к каждому запросу:
```bash
GET /profile HTTP/1.1
Host: example.com
Cookie: session_id=abc123xyz
```

### Атрибуты куки - важны для безопасности
- HttpOnly - кука недоступна из JavaScript (document.cookie ее не увидит).Защита от XSS-атак, который пытаются украсть куку через вредноносный скрипт
- Secure - кука отправляет только по HTTPS, никогда по обочному HTTP
- SameSite - контролирует, отправляется ли кука при переходе на другой сайт:
    - Strict - никогда не отправляется межсайтово
    - Lax - отправляется при обычной навигации(клик по ссылке), но не при фоновых запросах с других сайтов
    - None - отправляется всегда
  - Это прямая защита от CSRF-атак
- Path - на какие пути сайта кука действует (/admin - только для админки)
- Expires/Max-Age - когда кука истекает. Без этого - session cookie, живет только пока открыт браузер

# Sessions - как это связано с куками
## Что это - это состояние, которое сервер хранит у себя ( в памяти или базе данных) для конкретного пользователя между запросами. Кука с session_if - это просто "ключ", по которому сервер находит сессию в свое хранилище

### Процесс целиком:
1. Ты вводишь логин/пароль -> POST /login
2. Сервер проверяет данные, создает новую сессию у себя (например, session_id: abc123 -> user: konstantin, logged_in: true)
3. Сервер отправляет тебе куку с этим session_id через Set-Cookie
4. На каждый следующий запрос браузер отправляет эту куку
5. Сервер смотрит на session_id, находит в своей базе, что это ты залогинен - и отдает персонализированный ответ

Практическа уязвимость - Session Hijacking
Если атакующий каким-то образом узнаёт твой session_id (например, украл через XSS без HttpOnly, или перехватил по незашифрованному HTTP без Secure) — он может подставить эту же куку в свой браузер и стать тобой для сервера, без пароля вообще. Это прямая практическая причина, почему флаги HttpOnly/Secure/SameSite критичны
