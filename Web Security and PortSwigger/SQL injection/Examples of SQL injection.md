# Examples of SQL injection
Существует множество уязвимостей, атак и методов SQL-инъекций, которые встречаются в различных ситуациях. Некоторые распространенные примеры SQL-инъекций включают:

- Извлечение скрытых данных , позволяющее изменять SQL-запрос для получения дополнительных результатов
- Подрыв логики приложения , когда можно изменить запрос таким образом, чтобы он вмешивался в логику приложения
- UNION-атаки позволяют извлекать данные из разных таблиц базы данных
- Слепая SQL-инъекция — это инъекция , при которой результаты контролируемого вами запроса не возвращаются в ответах приложения

## Retrieving hidden data
Представьте себе приложение для онлайн-покупок, которое отображает товары в разных категориях. Когда пользователь нажимает на категорию «Подарки» , его браузер запрашивает URL-адрес:
```https://insecure-website.com/products?category=Gifts```
В результате приложение выполняет SQL-запрос для получения сведений о соответствующих товарах из базы данных:
```SELECT * FROM products WHERE category = 'Gifts' AND released = 1```
Этот SQL-запрос запрашивает у базы данных следующий результат:

- все подробности ( ```*```)
- со ```products``` стола
- где ```category``` находится ```Gifts```
- и ```released``` есть ```1```

Это ограничение ```released = 1``` используется для сокрытия продуктов, которые еще не выпущены. Можно предположить, что для невыпущенных продуктов ```released = 0```

В приложении отсутствуют средства защиты от SQL-инъекций. Это означает, что злоумышленник может, например, осуществить следующую атаку:
```https://insecure-website.com/products?category=Gifts'--```
В результате получается SQL-запрос:
```SELECT * FROM products WHERE category = 'Gifts'--' AND released = 1```
Важно отметить, что ```--``` это индикатор комментария в SQL. Это означает, что остальная часть запроса интерпретируется как комментарий, фактически удаляя его. В этом примере это означает, что запрос больше не включает в себя ```AND released = 1```. В результате отображаются все товары, включая те, которые еще не выпущены.

Аналогичным методом атаки можно заставить приложение отображать все товары в любой категории, включая категории, о которых оно не знает:
```https://insecure-website.com/products?category=Gifts'+OR+1=1--```
В результате получается SQL-запрос:
```SELECT * FROM products WHERE category = 'Gifts' OR 1=1--' AND released = 1```
Модифицированный запрос возвращает все элементы, где либо ```category``` равно ```Gifts```, либо ```1``` равно ```1```. Поскольку ```1=1``` всегда истинно, запрос возвращает все элементы.

## Subverting application logic
Представьте себе приложение, позволяющее пользователям входить в систему с помощью имени пользователя и пароля. Если пользователь вводит имя пользователя wienerи пароль bluecheese, приложение проверяет учетные данные, выполняя следующий SQL-запрос:
```SELECT * FROM users WHERE username = 'wiener' AND password = 'bluecheese'```
Если запрос возвращает данные пользователя, то вход в систему считается успешным. В противном случае он отклоняется

В этом случае злоумышленник может войти в систему под любым пользователем без необходимости ввода пароля. Он может сделать это, используя последовательность комментариев SQL --для удаления проверки пароля из ```WHERE``` условия запроса. Например, отправка имени пользователя ```administrator'--``` и пустого пароля приводит к следующему запросу:
```SELECT * FROM users WHERE username = 'administrator'--' AND password = ''```
Этот запрос возвращает пользователя, под которым ```username``` успешно ```administrator``` авторизован злоумышленник

## Retrieving data from other database tables
В случаях, когда приложение отвечает результатами SQL-запроса, злоумышленник может использовать уязвимость SQL-инъекции для получения данных из других таблиц в базе данных. Вы можете использовать UNIONключевое слово для выполнения дополнительного SELECTзапроса и добавления результатов к исходному запросу

Например, если приложение выполняет следующий запрос, содержащий ввод пользователя Gifts:
```SELECT name, description FROM products WHERE category = 'Gifts'```
Злоумышленник может отправить следующие данные:
```' UNION SELECT username, password FROM users--```
В результате приложение возвращает все имена пользователей и пароли, а также названия и описания товаров

## Blind SQL injection vulnerabilities
Многие случаи SQL-инъекций представляют собой «слепые» уязвимости. Это означает, что приложение не возвращает результаты SQL-запроса или подробную информацию об ошибках базы данных в своих ответах.

В зависимости от характера уязвимости и используемой базы данных для эксплуатации уязвимостей, связанных со слепой SQL-инъекцией, могут применяться следующие методы:
- Вы можете изменить логику запроса, чтобы вызвать заметное изменение в ответе приложения в зависимости от истинности одного условия. Это может включать в себя добавление нового условия в какую-либо логическую операцию или условное возникновение ошибки, например, деления на ноль
- Вы можете условно запускать задержку по времени при обработке запроса. Это позволяет определить истинность условия на основе времени, необходимого приложению для ответа
- С помощью методов OAST можно инициировать внеполосное сетевое взаимодействие. Этот метод чрезвычайно эффективен и работает в ситуациях, когда другие методы не помогают. Часто можно напрямую передавать данные через внеполосный канал. Например, можно поместить данные в DNS-запрос для домена, который вы контролируете

## Second-order SQL injection
SQL-инъекция первого порядка происходит, когда приложение обрабатывает ввод пользователя из HTTP-запроса и небезопасным образом включает этот ввод в SQL-запрос

SQL-инъекция второго порядка происходит, когда приложение получает ввод пользователя из HTTP-запроса и сохраняет его для дальнейшего использования. Обычно это делается путем помещения ввода в базу данных, но уязвимость не возникает в точке хранения данных. Позже, при обработке другого HTTP-запроса, приложение извлекает сохраненные данные и небезопасным образом включает их в SQL-запрос. По этой причине SQL-инъекция второго порядка также известна как хранимая SQL-инъекция

SQL-инъекции второго порядка часто происходят в ситуациях, когда разработчики знают об уязвимостях SQL-инъекций и поэтому безопасно обрабатывают первоначальную подачу данных в базу данных. При последующей обработке данные считаются безопасными, поскольку они были ранее безопасно помещены в базу данных. На этом этапе данные обрабатываются небезопасным способом, поскольку разработчик ошибочно считает их надежными

## Examining the database
Некоторые основные особенности языка SQL реализованы одинаково на популярных платформах баз данных, поэтому многие способы обнаружения и использования уязвимостей SQL-инъекций работают идентично на разных типах баз данных

Однако между распространенными базами данных существует множество различий
Например:

- Синтаксис для конкатенации строк
- Комментарии
- Пакетные (или сгруппированные) запросы
- API, специфичные для конкретной платформы
- Сообщения об ошибках

Вы можете запросить сведения о версии базы данных. Для разных типов баз данных подходят разные методы. Это означает, что если вы найдете подходящий метод, вы сможете определить тип базы данных. Например, в Oracle вы можете выполнить:
```SELECT * FROM v$version```

Вы также можете определить, какие таблицы базы данных существуют и какие столбцы они содержат. Например, в большинстве баз данных для получения списка таблиц можно выполнить следующий запрос:
```SELECT * FROM information_schema.tables```

## How to prevent SQL injection
Большинство случаев SQL-инъекций можно предотвратить, используя параметризованные запросы вместо конкатенации строк внутри запроса. Такие параметризованные запросы также известны как «подготовленные операторы»

Приведенный ниже код уязвим для SQL-инъекций, поскольку пользовательский ввод напрямую добавляется в запрос:

```
String query = "SELECT * FROM products WHERE category = '"+ input + "'";
Statement statement = connection.createStatement();
ResultSet resultSet = statement.executeQuery(query);
```
Этот код можно переписать таким образом, чтобы ввод пользователя не влиял на структуру запроса:
```
PreparedStatement statement = connection.prepareStatement("SELECT * FROM products WHERE category = ?");
statement.setString(1, input);
ResultSet resultSet = statement.executeQuery();
```
Параметризованные запросы можно использовать в любой ситуации, когда в запросе присутствуют ненадежные входные данные, включая ```WHERE``` условие и значения в операторе ```INSERT``` ИЛИ ```UPDATE```

Функциональность приложения, которая помещает ненадежные данные в эти части запроса, требует иного подхода, например:

- Внесение в белый список разрешенных входных значений
- Использование различной логики для обеспечения требуемого поведения

Для эффективной защиты от SQL-инъекций параметризованный запрос должен всегда представлять собой жестко закодированную константу. Он никогда не должен содержать переменных данных какого-либо происхождения. Не следует пытаться определять достоверность данных в каждом конкретном случае и продолжать использовать конкатенацию строк в запросе только для случаев, которые считаются безопасными
