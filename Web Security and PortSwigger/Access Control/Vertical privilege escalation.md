# Vertical privilege escalation(Вертикальное повышение привилегий) - Если пользователь получает доступ к функциям, к которым у него нет доступа, это считается вертикальным повышением привилегий

# Unprotected functionality(Незащищенная функциональность) - В самом простом виде вертикальное повышение привилегий возникает, когда приложение не обеспечивает никакой защиты для конфиденциальных функций

Например, на веб-сайте может размещаться конфиденциальная информация по следующему URL-адресу:
```https://insecure-website.com/admin```

Доступ к этой функции может быть предоставлен любому пользователю, а не только администраторам, имеющим ссылку на неё в своём пользовательском интерфейсе
В некоторых случаях административный URL-адрес может быть указан в других местах, например, в robots.txt файле:
```https://insecure-website.com/robots.txt```

Даже если ссылки нету, злоумышленник может использовать список слов для перебора адреса
В некоторых случаях конфиденциальная функциональность скрывается путем присвоения ей менее предсказуемого URL-адреса.

Это пример так называемой «безопасности за счет сокрытия». Однако сокрытие конфиденциальной функциональности не обеспечивает эффективного контроля доступа, поскольку пользователи могут обнаружить зашифрованный URL-адрес различными способами

Например функции админа находятся по следующему URl-адресу: ```https://insecure-website.com/administrator-panel-yb556```

Злоумышленник, возможно, не сможет угадать это напрямую. Однако приложение всё равно может раскрыть URL-адрес пользователям. URL-адрес может быть раскрыт в JavaScript-коде, который формирует пользовательский интерфейс на основе роли пользователя:
```
<script>
	var isAdmin = false;
	if (isAdmin) {
		...
		var adminPanelTag = document.createElement('a');
		adminPanelTag.setAttribute('href', 'https://insecure-website.com/administrator-panel-yb556');
		adminPanelTag.innerText = 'Admin panel';
		...
	}
</script>
```

# Parameter-based access control methods(Методы контроля доступа на основе параметров) - Некоторые приложения определяют права доступа или роль пользователя при входе в систему, а затем сохраняют эту информацию в месте, доступном пользователю.
Это может быть:
- Скрытое поле
- Файл cookie
- Предварительно заданный параметр строки запроса

Приложение принимает решения по контролю доступа на основе предоставленного значения 
```
https://insecure-website.com/login/home.jsp?admin=true
https://insecure-website.com/login/home.jsp?role=1
```
Этот подход небезопасен, поскольку пользователь может изменить значение и получить доступ к функциям

# Broken access control resulting from platform misconfiguration(Нарушение контроля доступа в результате неправильной настройки платформы) - ограничение доступа к определенным URL-адресам и методам HTTP в зависимости от роли пользователя

Например: ```DENY: POST, /admin/deleteUser, managers```
Это правило запрещает доступ к POST методу по указанному URL /admin/deleteUser для пользователей из групп менеджеров

Если веб-сайт использует строгие средства контроля доступа на стороне клиента, ограничевающие доступ на основе URL, но приложение позволяет переопределить URl через заголовок запроса, то может быть возможно обойти контроль доступа, используя запрос: 
```
POST / HTTP/1.1
X-Original-URL: /admin/deleteUser
```

Некоторые фреймворки для разработки приложений поддерживают различные нестандартные HTTP-заголовки, которые можно использовать для переопределения URL-адреса в исходном запросе, например X-Original-URL, и X-Rewrite-URL
